### [P0-1] ✅ PostgreSQL `execute()` 对无 id 列的表追加 `RETURNING id` 导致流量配额失效

- **来源**：数据库层审计 #001 / #002
- **位置**：[database/postgres.js:77-97](file:///d:/personal/cc/PenMark/database/postgres.js#L77-L97) + [事务内 execute](file:///d:/personal/cc/PenMark/database/postgres.js#L114-L131)
- **前因**：
  `execute()` 函数对所有 `INSERT` 语句自动追加 `RETURNING id` 以获取自增主键。但 `user_asset_bandwidth` 表的主键是复合键 `(user_id, month_start)`，没有 `id` 列。`assets.js:93-105` 的 `recordBandwidth` 使用 `INSERT ... ON CONFLICT DO UPDATE` 写入流量，PostgreSQL 执行时因 `RETURNING id` 引用不存在的列而报错。错误被 `recordBandwidth` 的 `try/catch` 静默吞掉（`console.warn` 后继续），导致流量永远写不进去。
- **后果**：
  - `checkQuota` 读 `usedBw` 恒为 0，普通用户 500MB/月流量配额形同虚设
  - 任意用户可无限拉取图片资源，耗尽服务器带宽
  - PostgreSQL 模式下该问题完全静默，日志只有 warn 级别
- **修复方案**（已实施）：
  - 检测 SQL 是否含 `ON CONFLICT` 或 `RETURNING`，含则跳过追加 `RETURNING id`
  - `insertId` 仅在追加 `RETURNING id` 的情况下尝试读取
  - `Number()` 转换增加 `Number.isFinite` 校验，防御 TEXT 类型主键（如 `media_assets` 的 UUID）返回 NaN
- **注意事项**：
  - SQLite 的 `execute()` 用 `lastInsertRowid` 不受影响，无需改动
  - 修复后需验证 PostgreSQL 模式下 `recordBandwidth` 不再报错，`checkQuota` 能正确读到累计流量
  - 如果将来有其他无 id 列的表走 `INSERT`（非 ON CONFLICT），仍会出问题；建议后续重构为调用方显式指定 `RETURNING` 列
  - **回归测试**：构造 PostgreSQL 环境跑一次图片访问，确认 `user_asset_bandwidth` 表有数据写入

### [P0-2] ✅ SQLite `convertPlaceholders` 的 $N 占位符顺序陷阱

- **来源**：此前修复（summary 记录）+ 数据库层审计 #018
- **位置**：[database/sqlite.js:13-15](file:///d:/personal/cc/PenMark/database/sqlite.js#L13-L15)
- **前因**：
  SQLite 的 `?` 占位符按出现顺序绑定参数，而 PostgreSQL 的 `$N` 按数字绑定。原 `convertPlaceholders` 直接把 `$N` 替换为 `?`，要求业务 SQL 中 `$N` 的数字顺序必须与出现顺序一致。任何 `$2` 出现在 `$1` 之前的 SQL，SQLite 会静默绑定错参数（不报错，但数据错位）。
- **后果**：
  - 跨数据库行为不一致，SQLite 模式下可能查到/写到错误数据
  - 极难排查——没有错误，只有数据异常
- **修复方案**（已实施）：
  `convertPlaceholders` 收集 `$N` 出现顺序，按数字重排 `params` 数组，消除对 SQL 文本顺序的依赖。
- **注意事项**：
  - 修复后所有 `$N` 占位符的 SQL 在 SQLite/PostgreSQL 下行为一致
  - 新增 SQL 时不再需要关心 `$N` 的出现顺序
  - **回归测试**：跑 `npm test` 确认现有测试通过

## P1 — 高危

### [P1-1] ❌ SSRF：`fetchImageAsBase64` / `fetchOG` 仅校验 hostname 字符串，未校验解析后 IP

- **来源**：后端审计 #1
- **位置**：[server.js:384-410](file:///d:/personal/cc/PenMark/server.js#L384-L410)（`isPrivateHost` + `fetchImageAsBase64`）、[server.js:502](file:///d:/personal/cc/PenMark/server.js#L502)（`fetchOG`）
- **前因**：
  `isPrivateHost(parsed.hostname)` 只做字符串匹配（`localhost` / `127.0.0.1` / `169.254.x.x` / `10.x` / `192.168.x` 等）。攻击者注册一个域名，A 记录指向 `127.0.0.1` 或 `169.254.169.254`（云 metadata 端点），字符串校验通过，但实际请求打到内网。
- **后果**：
  - `/api/proxy-image?url=http://evil.com/x.png` 会把内网响应体以 base64 返回给调用者
  - 可窃取云厂商 metadata 凭据（AWS/Azure/GCP 的实例 IAM token）
  - 可扫描内网端口、访问内网 API
  - 任意登录用户即可利用（`/api/proxy-image` 需登录，`/api/og` 可能不需要）
- **修复建议**：
  1. 先用 `dns.lookup(hostname, { all: true })` 解析所有 A/AAAA 记录
  2. 对每个 IP 做 `isPrivateIP(ip)` 校验（用 `ipaddr.js` 库或手写 IPv4/IPv6 私有段判断）
  3. 全部通过后再发请求
  4. **注意 DNS rebinding**：解析后到发请求之间 IP 可能变——理想方案是用解析到的 IP 直连（`https://<ip>/`），保留原 Host 头/SNI；但这对 HTTPS 证书校验有影响，需权衡
- **注意事项**：
  - `dns.lookup` 是异步的，需把 `isPrivateHost` 改成 `async`
  - IPv6 私有地址段（`::1` / `fc00::/7` / `fe80::/10`）也要拦截
  - 不要只校验第一个 IP，要校验所有解析结果（防止 round-robin DNS 绕过）
  - 云环境 metadata 端点 `169.254.169.254` 是最高优先级拦截目标
  - 修复后 `/api/proxy-image` 和 `/api/og` 都要覆盖

### [P1-4] ❌ SQLite 侧外键缺失 `ON DELETE CASCADE`

- **来源**：数据库层审计 #004 / #013 / #019 / #028
- **位置**：[db.js:50-398](file:///d:/personal/cc/PenMark/db.js#L50-L398)（多张表）
- **前因**：
  `db.js` 中 SQLite 的 `shares` / `reports` / `document_versions` / `ai_chat_history` / `editor_actions` / `media_assets` / `import_batches` / `user_asset_bandwidth` 表的外键均无 `ON DELETE CASCADE`，且部分表（`documents` / `folders` / `shares` 等）连 `FOREIGN KEY (user_id) REFERENCES users(id)` 声明都没有。而 PostgreSQL 迁移文件 001 等都有 `REFERENCES users(id) ON DELETE CASCADE`。SQLite 与 PG schema 不对等，目前靠应用层手动删除兜底。
- **后果**：
  - 一旦新增删除路径遗漏手动清理，SQLite 留孤儿行
  - `PRAGMA foreign_keys=ON` 形同虚设（无外键声明就没有约束）
  - 删用户后 SQLite 不级联清理任何关联数据
- **修复建议**：
  1. 在 `db.js` 的 `CREATE TABLE` 中为所有外键补 `REFERENCES users(id) ON DELETE CASCADE`
  2. 对于已建表的 SQLite，需用 `PRAGMA writable_schema=1` + 直接改 `sqlite_master`（SQLite 不支持 `ALTER TABLE ADD CONSTRAINT`）
  3. 或在迁移中重建表（`CREATE TABLE _new` → `INSERT INTO _new SELECT` → `DROP old` → `ALTER TABLE _new RENAME`）
- **注意事项**：
  - SQLite 改表结构非常麻烦，建议写一次性迁移脚本
  - 改完后确认 `PRAGMA foreign_keys=ON` 在每次连接时都执行
  - PG 侧不受影响（迁移文件已正确）
  - **风险**：补 CASCADE 后，删用户会级联删除大量数据，确保这是期望行为

### [P1-5] ❌ 多个文档端点遗漏 `deleted_at IS NULL` 过滤

- **来源**：数据库层审计 #006 / #007 / #008
- **位置**：
  - [server.js:689](file:///d:/personal/cc/PenMark/server.js#L689) `GET /api/documents/:id`
  - [server.js:1094](file:///d:/personal/cc/PenMark/server.js#L1094) `GET /api/documents/:id/version`
  - [server.js:2054](file:///d:/personal/cc/PenMark/server.js#L2054) `POST /api/documents/:id/share`
- **前因**：
  这三个端点校验文档归属时 `SELECT ... FROM documents WHERE id=$1 AND user_id=$2` 未加 `AND deleted_at IS NULL`。已软删除的文档仍可被拥有者按 ID 读到正文、轮询版本号、创建分享。与 `GET /api/documents` 列表的回收站语义不一致。
- **后果**：
  - 拥有者可对已删除文档创建分享（虽然公开访问端点有 `deleted_at IS NULL` 会 404，但会创建无用 `shares` 记录）
  - 回收站中的文档内容可被直接读取，语义混乱
  - 误导用户以为文档已恢复
- **修复建议**：
  三处 SQL 补 `AND deleted_at IS NULL`。
- **注意事项**：
  - `GET /api/documents/:id` 如果有"回收站预览"用途则不能直接加——需确认前端是否有回收站预览功能
  - 如果回收站预览走的是另一个端点，直接加过滤即可
  - `POST /api/documents/:id/share` 加过滤后，对已删除文档创建分享应返回 404

### [P1-6] ❌ `POST /api/reports` 的 `doc_id` 未校验归属

- **来源**：数据库层审计 #009
- **位置**：[server.js:1929](file:///d:/personal/cc/PenMark/server.js#L1929)
- **前因**：
  `POST /api/reports` 的 `doc_id` 直接从 `req.body` 传入 `INSERT`，未做 `Number.isInteger` 校验，未校验文档存在或归属/分享关系。任何登录用户可对任意 `doc_id`（含他人私有文档 ID）提交举报，仅靠外键挡住不存在的 ID。

- **注意事项**：
  - 分享文档的访客也应能举报——校验逻辑要包含分享关系
  - 不要泄露文档是否存在（对无权访问的 doc_id 返回相同的"举报已提交"或 404，避免枚举）

#### [P2-F1] ❌ `insertLink` 的 `|| url.trim()` 回退绕过 URL 白名单

- **来源**：前端审计 #1
- **位置**：[public/editor.js:350](file:///d:/personal/cc/PenMark/public/editor.js#L350)
- **前因**：
  ```js
  document.execCommand('createLink', false, this._normalizeUrl(url) || url.trim());
  ```
  `_normalizeUrl` 对非 http/https/域名 URL 返回空串（包括 `javascript:`），但 `|| url.trim()` 回退把原始输入直接传给 `createLink`，可生成 `<a href="javascript:alert(1)">`。主站文档内容服务端不做清洗（仅分享页走 `sanitizeShareContent`），故该链接会持久化在文档中，点击即执行。
- **后果**：存储型 XSS，用户点击链接即执行任意 JS。
- **修复建议**：删除 `|| url.trim()` 回退，`_normalizeUrl` 返回空时直接 `return` 中止插入。
- **注意事项**：
  - 修复后用户输入 `javascript:` 链接会静默失败——可考虑加一个提示
  - 自动链接（editor.js:2569）已用 `_normalizeUrl` 无回退，是安全的，对照参考
  - 修复后要检查分享页 `sanitizeShareContent` 是否也会拦截 `javascript:` 链接（双重防御）
